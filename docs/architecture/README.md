# Архитектура

## Назначение

Проект представляет собой учебную Python-библиотеку для декларативного описания и пошагового исполнения взаимодействующих автоматных объектов CIAO. Библиотека не является IDE или визуальным редактором.

## Предварительное разделение ответственности

### Доменная модель

Содержит декларативное описание программы: автоматные классы и объекты, состояния, операции, переходы и соединения. Этот слой не знает об очереди сообщений, цикле Tkinter и текущем состоянии исполнения.

### Инфраструктура исполнения

Проверяет и компилирует декларативную модель, хранит независимое состояние экземпляров, маршрутизирует операции, обрабатывает FIFO-очередь команд и формирует трассу выполнения.

### Визуализация

Содержит необязательные Tkinter-адаптеры, конкретные представления примеров и односторонний экспортер draw.io. Визуализация не изменяет внутреннее устройство runtime; экспортер работает с проверенным `CompiledProgram` без запуска исполнения.

## Согласованная основа декларативного API

- Комбинации `COMMAND`/`QUERY` и `PROVIDED`/`REQUIRED` представлены четырьмя публичными декораторами: `@provided_command`, `@required_command`, `@provided_query`, `@required_query`.
- Внутри они создают одну модель `Operation`; универсальный параметризованный декоратор не является основным пользовательским API.
- `@guard` и `@action` отмечают локальные элементы перехода. Они не являются операциями и не могут быть конечными точками `Connection`.
- `@guard(text="...")` и `@action(text="...")` сохраняют необязательное пользовательское описание для диаграммы. Required-команды и required-query также поддерживают параметризованную форму с `text`; эти метаданные не влияют на компиляцию и исполнение.
- `@action(emit=command)` декларирует одну потенциальную required-команду и требует параметр `Emit`; `@action(emits=(...))` внедряет `Emits`.
- `@guard(query=operation)` и `@action(query=operation)` требуют параметр `Query`; формы `queries=(...)` внедряют `Queries`. Query- и Emit-формы можно сочетать в одном Action, используя два отдельных DI-параметра.
- Переход объявляется через `transition(...)`, содержит не более одного условия, упорядоченный кортеж действий и необязательный признак `otherwise=True`. Резервная ветвь не содержит Guard и выбирается только тогда, когда все Guard её группы ложны.
- Компилятор проверяет сигнатуры по аннотациям типов: результат `Guard` должен иметь тип `bool`, результат `Action` — `None`, а параметры события должны быть совместимы с запускающей операцией.
- Компилятор валидирует группы `(source, event)`, запрещает смешение безусловных и условных альтернатив и выдаёт `MissingOtherwiseWarning` для неполной условной группы.
- `State(final=True)` задаёт явную финальную семантику для анализа и визуализации, но не останавливает runtime.
- Provided-декораторы принимают необязательный `external=True`. Внешней является только явно отмеченная операция; имя метода не имеет специального значения.
- Роль задаётся выбором Generic-базы: `Automaton[ContextT]`, `ControllerAutomaton[ContextT]` или `ViewAutomaton[ContextT]`. Соответствующие значения `AutomatonRole` — `BASE`, `CONTROLLER`, `VIEW`; роль не влияет на исполнение.

Декораторы сохраняют декларативные метаданные, но не исполняют пользовательский код и не могут доказать чистоту условия.

Компилятор один раз разрешает аннотации операций и сохраняет неизменяемые `OperationSignature` в `AutomatonDefinition`. Инфраструктура исполнения и визуализаторы используют эти проверенные метаданные, не вызывая собственный повторный `get_type_hints()` для операций.

## Контекст автоматного объекта

Пользователь объявляет тип локального состояния наследником `AutomatonContext`. Поля наследника доступны обработчикам напрямую:

```python
@dataclass
class ControllerContext(AutomatonContext):
    values: list[int]
    index: int = 0
    total: int = 0
```

Тип связывается с автоматом через Generic, например `class Controller(ControllerAutomaton[ControllerContext])`. `Runtime` владеет контекстами и создаёт отдельный экземпляр для каждого `AutomatonObject` в каждом запуске. Декларативный класс автомата не хранит текущие значения. Обработчик получает только контекст объекта-адресата; доступ к другим объектам осуществляется через требуемые операции и `Connection`.

Исходящая required-команда явно указывается в метаданных `Action`:

```python
@action(emit=draw)
def publish(self, ctx: ControllerContext, emit: Emit) -> None:
    emit(total=ctx.total)
```

`Emit` уже привязан к команде, объекту-источнику и текущему runtime. Он действует только во время одного вызова `Action`, а команды буферизуются до успешного завершения всего перехода. Для нескольких команд используется `emits[self.command](...)`. Публичный `Automaton.emit(...)` удалён, чтобы компилятор и экспортёр видели полный набор потенциальных исходящих команд.

Требуемый запрос явно указывается в метаданных Guard или Action:

```python
@guard(query=read_limit)
def below_limit(self, ctx: ControllerContext, query: Query) -> bool:
    return ctx.total < query()
```

`Query` привязан к одной required-query, а `Queries` выбирает одну из нескольких объявленных операций по identity: `queries[self.read_limit]()`. Обе capability действуют только во время текущего вызова обработчика, синхронно проходят по `Connection`, не создают FIFO-сообщение и не кэшируют результат. Контекст содержит только пользовательские данные и больше не хранит скрытую runtime-привязку. Публичного `Automaton.query(...)` нет, поэтому потенциальные запросы полностью видны компилятору и экспортёру.

Для внешнего наблюдения runtime возвращает снимок состояния, а не изменяемую ссылку на внутренний контекст. Это сохраняет независимость объектов и позволяет повторно запускать одну декларативную программу.

## Протокол учебного примера суммы массива

`SumController` использует промежуточное состояние `publishing`, чтобы публикация снимка была видна в автоматной модели. Переход по `tick` из `running` при допустимом индексе вычисляет очередную сумму, помещает `draw` в FIFO и переводит Controller в `publishing`. `SumView` применяет снимок и асинхронно отправляет обратную команду `draw_completed`; только её обработка возвращает Controller в `running`.

Оба перехода по `tick` из `running` выражают одну бинарную развилку. Обычный Guard `has_current` проверяет, что индекс находится внутри массива; при ложном результате явная ветвь `otherwise=True` переводит Controller в нефинальное `completed`. Из него `reset` очищает контекст и возвращает автомат в `idle`, а отдельный явный `tick` переводит его в терминальное `done`. Отсутствие команды не считается событием.

Runtime вычисляет все Guard группы ровно по одному разу в декларативном порядке, не используя порядок как приоритет. Единственный истинный Guard выбирается вместо `otherwise`; несколько истинных дают `AmbiguousTransitionError`; исключение Guard прекращает выбор. Имя выбранного class-атрибута сохраняется в `StepResult.transition` и `TraceEvent.transition`. Для ошибки Action оно остаётся доступным, а до выбора ветви равно `None`.

## Экспорт draw.io

Публичная функция `ciao.visualization.drawio.export_program_drawio(program, path)` выполняет следующий конвейер:

```text
Program → compile_program() → builder → layout → XML writer → .drawio
```

- `compile_program()` вызывается ровно один раз;
- builder читает `AutomatonDefinition`, `OperationSignature` и `routes`;
- layout сначала измеряет весь видимый текст, затем рассчитывает внутренний граф,
  рамки блоков и только после этого межблочные связи;
- writer только сериализует готовые координаты через `xml.etree.ElementTree`;
- запись атомарна: прежний файл заменяется лишь после успешной сериализации временного файла в том же каталоге.

Операции, состояния, Decision-узлы и assembly-связи остаются нативными редактируемыми элементами draw.io. Область автомата имеет белый фон, а обычные состояния и стрелки переходов получают цвет роли (`Controller` — голубой, `View` — зелёный). Для `State(initial=True)` создаются отдельная чёрная точка Entry и стрелка к состоянию. `State(final=True)` изображается самостоятельным Exit с редактируемой подписью имени; исходящие переходы из final-состояния не отбрасываются, поскольку runtime их допускает.

Внешний `provided` endpoint с `external=True` рисуется самостоятельным lollipop над границей блока и не соединяется служебной линией со State: принадлежность события переходу видна по подписи перехода. Видимые provided/required-операции получают компактную сигнатуру `name(parameters)` из проверенной `OperationSignature`: показываются имена параметров и defaults, но не типы, `self` или `ctx`. Полная типизированная сигнатура сохраняется в XML-метаданных `ciaoSignature`. Имя автоматного объекта и его класса включено в цветную карточку контекста, а не дублируется на белой области блока.

Подпись события перехода использует ту же сигнатуру provided-операции. Обычный action отображается собственным именем. Если у guard/action указан `text`, визуализатор добавляет `name: text`; имя обычного action выделяется жирным, а пользовательский текст остаётся без дополнительного оформления. Потенциальные синхронные запросы выводятся внутри той же подписи отдельным красным блоком `<<Query>>:` в порядке декларации; `text` required-query показывается рядом с её сигнатурой. Ветка `otherwise` подписывается `[else]`, располагается после Guard-ветвей и сохраняет `ciaoOtherwise=true`. Для action с `emit`/`emits` собственные имя и `text` не выводятся — остаются Query-блок и сигнатуры исходящих required-команд в порядке кортежа декоратора. Имя самого `Transition` остаётся в метаданных, но не раздувает видимый текст.

Action без `emit`/`emits` дополнительно получает на нижней границе автомата
компактную текстовую декларацию без socket-фигуры. Ширина поля определяется
именем Action, а исходная сигнатура и `text` сохраняются в XML-метаданных самой
подписи. Action с исходящей командой отдельной декларацией не дублируется.

Каждый обычный action и каждая команда из `emit`/`emits` выводятся с новой структурной строки. Символ `/` отмечает начало общего блока действий и ставится только перед первой строкой. Автоматические переносы внутри самой сигнатуры или `text` не добавляются; явные переводы строк из пользовательского `text` сохраняются. Edge-label получает вычисленные `width`/`height` по самой длинной строке и числу строк, поэтому поле можно изменять в draw.io. Раскладка измеряет зазор от стороны этого прямоугольника до стрелки и выбирает ближайшую позицию без пересечения с состояниями, контекстом, Decision и уже размещёнными подписями.

Операция из `Program.connections` представляется составным assembly-интерфейсом в межблочном канале: от блока требующей стороны идёт половина с `halfCircle`, от предоставляющей — половина с `oval`; обе сходятся в общем невидимом узле. На самой связи показывается только имя required-операции. Query-связь использует ту же ненаправленную нотацию, но окрашивается в красный. Параллельные connections используют разные точки выхода на границах блоков и отдельные полосы. Их подписи остаются в межблочном канале и не заходят на прямоугольники автоматов. Семантические метаданные обеих операций сохраняются на половинах соединения, хотя отдельные endpoint-вершины для них не рисуются.

Компоновка выполняется детерминированным конвейером:

1. измеряются подписи переходов, Action и операций без автоматических переносов;
2. из сетки состояний, максимальных подписей и нижней зоны выводятся минимальные
   ограничения рамки;
3. резервируются ряды обычных и конечных состояний, Decision и Entry;
4. ортогональные варианты переходов оцениваются по пересечениям с узлами,
   общим участкам с уже выбранными маршрутами и длине участка под подпись;
5. подписи закрепляются на свободных участках, а занятые прямоугольники
   резервируются для следующих переходов;
6. на готовую нижнюю границу добавляются компактные Action-декларации и
   неподключённые lollipop/socket-интерфейсы;
7. после размещения всех блоков строятся assembly-connections.

Таким образом, длинная подпись участвует в выборе ширины блока, конечные состояния
получают отдельный ряд, а переход не должен проходить через посторонние State,
Decision, Entry или Exit. Порядок `Program.objects` сохраняется, количество
колонок выбирается детерминированно. XML ID строятся из имени `AutomatonObject` и
qualified name декларации с коротким стабильным хешем, поэтому вставка или
перестановка несвязанных объектов не меняет ID существующих элементов.

### Экспериментальная многофазная компоновка и benchmark

Публичный `export_program_drawio()` по-прежнему использует описанный выше
`layout_diagram()`; это baseline, и его контракт не изменён. Параллельно модуль
`layout_multiphase.py` реализует экспериментальную стратегию, доступную только
внутри адаптера визуализации и benchmark. Она получает тот же
`DiagramDescription` и проходит детерминированные фазы:

1. измеряет заголовок, подписи переходов, Action и операций;
2. перебирает допустимое число колонок состояний и оценивает логический span
   переходов, пустые ячейки, загрузку каналов и aspect ratio;
3. резервирует дополнительную ширину межколоночных каналов и высоту
   межстрочных каналов пропорционально числу маршрутов;
4. рассчитывает единую цветную карточку `object : AutomatonClass` и полей
   контекста и прижимает её к левому верхнему углу рамки без внешнего отступа;
5. размещает граф и нижнюю полосу Action/операций, после чего строит
   прежние assembly-connections между готовыми блоками.

Третья стратегия `layout_elk.py` использует ELK Layered через закреплённый
`elkjs`. Первый ELK-проход независимо размещает состояния, Entry, Exit и
Decision каждого автомата вместе с edge-label; второй размещает уже измеренные
автоматные блоки и ортогонально маршрутизирует assembly-connections. Полученные
координаты и bend points преобразуются обратно в обычные `NodeCell`/`EdgeCell`,
поэтому writer и формат `.drawio` не зависят от ELK. Вызов выполняется отдельным
Node.js-процессом; отсутствие Node или `elkjs` даёт явный `ElkUnavailableError`
и никак не влияет на baseline, runtime или domain.

Размер context-card вычисляется по заголовку и строкам полей, ограничивается
разумной максимальной шириной и учитывает прогнозируемые переносы длинных типов.
Название не создаёт отдельный `automatonTitle`: оно остаётся первой строкой того
же цветного прямоугольника, как в эталонной `sum_program.drawio`. Рядом с каждой
нижней Action-подписью создаётся перпендикулярный рамке UML required-interface —
фиксированная ножка с наконечником `halfCircle`, то есть та же нотация, что в
эталонной диаграмме. Provided-интерфейсы сохраняют
lollipop-обозначение. ELK не размещает эти граничные элементы: общий Python-
layout строит для всех стратегий детерминированную нижнюю полосу слева направо
по правилу «UML-значок, зазор 6 px, подпись», оставляя 18 px между соседними
парами. Ножка строится между двумя невидимыми якорями на расстоянии 24 px,
перпендикулярно нижней границе; размер подковы фиксирует `endSize=6`, а её
ориентацию задаёт направление ребра без ручного `rotation`. Поэтому расширение
внутреннего графа не может изменить размер или вид самого символа.

ELK использует компактный профиль spacing: расстояния между узлами, слоями,
стрелками и подписями уменьшены до минимальных значений, на которых benchmark
не фиксирует пересечений. Размер страницы выводится рядом с quality-метриками,
поэтому выигрыш в чистоте нельзя скрыть неограниченным увеличением листа.
Размер блока вычисляется по фактической границе ELK-графа, context-card и нижней
полосы интерфейсов; размеры multiphase-шаблона больше не используются как
минимум, поэтому простые автоматы не наследуют его пустые строки и каналы.
Порядок `NodeCell` берётся из шаблона: рамка автомата сериализуется раньше
Action-подписей, и цветной фон не может закрыть текст интерфейса.

Для плотного автомата применяется адаптивный профиль. Детерминированная
эвристика требует не менее четырёх состояний и хотя бы одну подпись перехода
шириной от 320 px. Внутренний граф переносится под context-card, а не
резервирует её ширину слева. Визуальная подпись перехода сохраняет событие,
имена Guard, Action, Query и emitted-команды, но сворачивает аргументы в `…` и
не повторяет длинный поясняющий `text`. Исходная HTML-подпись записывается в
`ciaoFullLabel`, поэтому сжатие не уничтожает информацию. Нижняя полоса Action
и UML-интерфейсов остаётся полной и не участвует в таком сокращении.

Все стратегии оцениваются функцией `evaluate_layout(DiagramPage)`. Метрика не
читает внутренние решения layout и включает:

- долю площади попарных перекрытий самостоятельных объектов;
- долю длины стрелок, проходящую через посторонние объекты;
- число точечных пересечений стрелок;
- долю длины стрелок, совпадающую с другими стрелками на коллинеарных участках;
- число edge-label, пересекающих любую стрелку, и отдельно собственную стрелку;
- среднее/максимальное расстояние от прямоугольника edge-label до его стрелки;
  первые 12 px считаются нормальным зазором, избыток нормируется на 100 px.

`quality_penalty` — агрегированная величина, где меньше лучше:
`1000*object_overlap + 1000*edge_object_overlap + 500*edge_overlap +
300*label_intersection_ratio + 50*label_distance_penalty + 2*edge_crossings`.
Все исходные компоненты сохраняются рядом, поэтому изменение весов не требует
повторной генерации диаграмм. Для рёбер с `exitX/exitY` и `entryX/entryY`
метрика использует фактическую точку на границе фигуры, а не центр блока.

Оба альтернативных pipeline являются экспериментами над геометрией, а не новым
публичным API. Смена стратегии в `export_program_drawio()` должна быть отдельным
согласованным решением после накопления benchmark-результатов.

## Текущее состояние

Реализация находится в пакете `ciao`. Она включает декларативную модель с явным `otherwise`, компиляцию и валидацию групп переходов, FIFO-runtime, синхронные запросы через `Query`/`Queries`, трассу с именем выбранной ветви, строгий/нестрогий режим и предел `run()`. Пример суммы разделён на автоматные классы `examples/array_sum/automatos`, сборку `examples/array_sum/program.py` и сценарии запуска; отдельный headless-пример Query DI находится в `examples/query_di.py`. Ключевая семантика покрыта тестами в `tests/`.

Необязательный пакет `ciao.visualization` экспортирует общий адаптер неизменяемых событий runtime в цикл Tkinter через `after` и функцию экспорта draw.io. Конкретные элементы интерфейса суммы массива не объявляются виджетами библиотеки: составное представление `ArraySumView` находится в `examples/array_sum/ui` и подключено в `examples/array_sum/array_sum_tk.py` без изменений ядра. Пример экспорта находится в `examples/export_drawio.py`.
